2. Resolução dos 7 achados do pentest original

✓
1. Exposição em projects e credenciais de clientes em texto puro CRÍTICO CORRIGIDO · PROVADO
anon = 0 linhas cofre project_credentials (100 registros) 0 chaves sensíveis em projects
fechar ▴

Antes (Pentest)

GET /rest/v1/projects?select=* com a anon key retornava projetos completos em HTTP 200, incluindo senhas de PostgreSQL, AnyDesk, SO e tokens Skills dentro de custom_fields.

Depois (Remediado)

Policy anônima neutralizada (USING (false) para não autenticados). Além disso, as 14 chaves sensíveis + subchaves secretas de dtc foram movidas de projects.custom_fields para a tabela dedicada public.project_credentials protegida por RBAC e invisível para anon.

O que foi implementado:

  • Neutralização da policy "Allow public select for active commercial checklists and roadma" em public.projects (TO authenticated USING (false)).
  • Criação da tabela cofre public.project_credentials com REVOKE ALL FROM PUBLIC, anon e policies RLS exclusivas para authenticated via has_permission(auth.uid(), 'project_credentials', 'view'/'edit').
  • Backfill integral para o cofre e remoção física das chaves de senha/token de projects.custom_fields em todos os registros, mantendo apenas metadados não sensíveis nas listagens (useProjectsList.ts).

Prova técnica em produção (Supabase okvufcwkophaadttmjwa):

-- Simulacao como papel anon em transacao controlada:
SELECT COUNT(*) FROM public.projects;             → 0 registros
SELECT COUNT(*) FROM public.project_credentials;  → ERROR 42501: permission denied (DENIED)

-- Auditoria do backfill no banco real:
vault_rows = 100 | dirty_projects_rows = 0 | dirty_dtc_rows = 0

2. IDOR no chat público (pos-chat) — listagem de visitantes e leitura de terceiros CRÍTICO CORRIGIDO · PROVADO
get_pos_chat_visitors bloqueada p/ anon token 256-bit + SHA-256 UX sem PIN mantida
fechar ▴

Antes (Pentest)

Qualquer pessoa com o UUID do link chamava get_pos_chat_visitors, obtinha os visitor_id reais dos funcionários do cartório e lia suas sessões e mensagens completas.

Depois (Remediado — Opção A)

A listagem pública de visitantes foi removida da interface e revogada do papel anon. Ao entrar com Nome + Setor, o servidor emite um token aleatório secreto (256 bits) e valida seu hash sha256 (access_token_hash) em toda leitura e escrita.

O que foi implementado:

  • REVOKE ALL ON FUNCTION public.get_pos_chat_visitors(uuid) FROM PUBLIC, anon e select_pos_chat_visitor(uuid, uuid) revogada de anon.
  • Nova coluna access_token_hash TEXT em public.pos_ai_chat_visitors; register_pos_chat_visitor retorna access_token (64 hex chars via dois UUIDs v4 concatenados) apenas na criação e persiste o digest SHA-256 no banco (tratando homônimos no mesmo setor com sufixo numérico automático).
  • Sobrecargas antigas sem token de get_pos_chat_visitor_sessions e get_pos_chat_session_messages revogadas; as novas exigem e validam p_visitor_token via verify_pos_chat_visitor_token antes de retornar dados.

Prova técnica em produção:

1) Chamada anon para listar visitantes do link público:
PERFORM public.get_pos_chat_visitors(project_id);      → DENIED: 42501 (permission denied)

2) Registro e validação de token emitido pelo servidor:
register_pos_chat_visitor(proj, 'Teste', 'TI')         → success: true (+ access_token único)
verify_pos_chat_visitor_session(proj, id, valid_tok)   → valid: true
verify_pos_chat_visitor_session(proj, id, forged_tok)  → valid: false

✓
4. Edge Function pos-assistant-chat sem posse de sessão e sem rate limit ALTO CORRIGIDO · DEPLOY v19
token SHA-256 30/min visitante · 200/h link teto 4000 chars verify_jwt=true
detalhes ▾

Correção aplicada na Edge Function pos-assistant-chat (implantada v19 em produção):

  • Autenticação do visitante: tanto action: "chat" quanto action: "feedback" exigem visitor_token, calculam o hash SHA-256 na função e conferem contra pos_ai_chat_visitors.access_token_hash (status 403 se inválido ou visitante inativo).
  • Vínculo estrito de sessão (anti-injeção): verifica se o session_id já possui mensagens associadas a outro visitor_id; em caso positivo, bloqueia com HTTP 403, impedindo injeção em conversas alheias.
  • Rate limiting em banco + teto de entrada: mensagens limitadas a 4.000 caracteres; bloqueio com HTTP 429 acima de 30 mensagens/minuto por visitante ou 200 mensagens/hora por projeto/link.
  • Sigilo de erros e CORS: removido o repasse de payloads brutos de erro da OpenAI e restringido Access-Control-Allow-Origin para hub.siplan.com.br e siplanhub.vercel.app.

5. Cadastro público aberto com autoconfirmação no Supabase Auth MÉDIO CORRIGIDO · DASHBOARD + BANCO
disable_signup = true Leaked Password Protection ON handle_new_user blindado
detalhes ▾

Defesa aplicada em duas camadas (Auth Dashboard + Banco de Dados):

  • Supabase Auth Dashboard: cadastro público de novos usuários desativado (Allow new users to sign up = OFF / disable_signup = true) e verificação contra senhas vazadas ativada (Leaked Password Protection = ON).
  • Defesa em profundidade no banco: public.handle_new_user() foi reescrita para ignorar qualquer campo role enviado no raw_user_meta_data, gravando invariavelmente 'user' (handle_new_user_reads_role_meta = false). A criação legítima de colaboradores permanece centralizada na Edge Function autenticada create-user.

detalhes ▾

3. Endurecimentos adicionais (auditoria white-box no código e banco)

Além dos 7 pontos externos do pentest, a auditoria direta no Supabase e no repositório identificou e fechou mais 7 vetores internos de risco:

8. Edge Functions fantasma desativadas HTTP 410

As funções legadas create-missing-users (v9) e migrate-team-members (v9), que existiam em produção criando usuários com senha padrão hardcoded, foram substituídas por respostas fixas HTTP 410 (Function deprecated and disabled) com verify_jwt: true.

9. Bloqueio de auto-escalação de privilégio 42501

Implementada a trigger trg_protect_profile_privileged_fields (SECURITY INVOKER) em public.profiles e neutralizada a policy legada profiles_update_own. Qualquer usuário sem users.edit é bloqueado ao tentar alterar a coluna role, mantendo edição normal de nome/perfil.

10. Segregação do cofre & Split Query RBAC

Criado o recurso project_credentials (view, edit) no catálogo RBAC e no banco. A listagem principal (useProjectsList) foi limpa de credenciais; detalhes são hidratados sob demanda em useProjectDetails e na abertura da Planilha de Ambientes (EnvironmentListDialog), evitando sobrescrita ao mover cards no Kanban.

11. Rotação da ponte Skills & RPC protegida ROTACIONADO

O segredo compartilhado skills_bridge_secret foi rotacionado sincronamente entre okvufcwkophaadttmjwa e bnulocsnxiffavvabfdj. A RPC get_project_skills_sibling_group agora exige projects.view (ou service_role) e valida project_credentials.view para devolver o token.

12. Storage privado (`project-files` e backups) PRIVATE

Ambos os buckets de documentos sensíveis tiveram public = false aplicado e policies restritas a authenticated, com migração no frontend de URLs públicas para createSignedUrl (backups do manual de conhecimento e anexos) mantendo o n8n operacional via service_role.

13. Edge Functions, Anti-SSRF & CORS estrito JWT + CORS

generate-routine-metadata (v2) e bunny-video-info (v2) passaram a exigir JWT + validações (assistants_knowledge.edit, whitelist de library 467408, GUID UUID e checagem de host b-cdn.net/mediadelivery.net). Todas as 7 functions ativas tiveram CORS travado para os domínios oficiais.

14. Higiene SQL, rotas extras & headers HTTP 43 → 0

search_path = public fixado em todas as funções de banco (zerando 43 advisors); triggers e RPCs de worker/n8n/BI revogadas de anon; rota /projects/:id/adherence?mode=print agora exige login + permissão; headers X-Content-Type-Options, X-Frame-Options, Referrer-Policy e Permissions-Policy adicionados em vercel.json.

5. Status do plano de ação do relatório original

CONCLUÍDO P0 — Contenção crítica e fechamento de superfície anônima

  1. Segregação de credenciais (PostgreSQL, AnyDesk/TeamViewer, SO, Orion Admin e tokens Skills) para cofre dedicado protegendo acessos existentes e rotação imediata da chave interna skills_bridge_secret entre HUB e Skills.
  2. Fechamento de RLS de projects para anon (0 registros retornados) e isolamento das listagens leves no frontend sem carregar senhas.
  3. Bloqueio de get_pos_chat_visitors para anon e remoção da listagem nominal pública de colegas.

CONCLUÍDO P1 — Identidade do visitante, Edge Functions e Auth

  1. Token opaco de 256 bits emitido no cadastro do visitante e validado via hash SHA-256 em todas as RPCs do pos-chat e na Edge Function pos-assistant-chat.
  2. Proteção da Edge Function contra injeção em sessão alheia (403), teto de 4.000 caracteres e rate limit em banco (30/min e 200/hora).
  3. Auditoria de privilégios de authenticated, trigger anti-escalação em profiles.role, fechamento de autocadastro público e ativação do Leaked Password Protection.

CONCLUÍDO P2 — Cofre, revisão de rotas públicas e higiene geral

  1. Revisão completa das demais rotas públicas (PublicChecklist via RPCs estritas, RoadmapPage via get_roadmap_data, PublicInfraCollection sem retorno anônimo aberto na tabela e fechamento do modo impressão em Aderência).
  2. Migração integral das credenciais de custom_fields para public.project_credentials com permissão granular em /admin/roles e proteção de armazenamento privado nos buckets.
  3. Redução total da exposição de notes e campos comerciais para anon, além de headers HTTP defensivos e testes estruturais de invariantes RLS.
Nota sobre entrega contínua: todas as correções de banco de dados (RLS, cofre, triggers, RPCs), rotação do segredo interno de bridge, configurações do Supabase Auth e as 9 Edge Functions já estão ativas em produção no projeto okvufcwkophaadttmjwa.
